# 毛利表重构规划文档

## 一、背景与问题分析

### 1.1 当前系统存在的问题

| 问题 | 描述 |
|------|------|
| **入库成本取值不可靠** | 入库单价含税从入库单 `warehousing_items.tax_included_price` 读取，该字段可能为0（手动添加商品行未填价格、从采购订单复制时价格为0等） |
| **匹配链路脆弱** | 出库单→销售订单→采购订单→入库单，依赖 `contract_number` 逐层匹配，任一环节断链则数据丢失 |
| **成本未真正核算** | 没有独立的"成本核算"环节，入库成本直接取单据上的价格，而非经过存货核算后的成本 |
| **费用分摊粗糙** | 所有费用按出库金额比例简单分摊，未考虑按数量、按重量等多种分摊方式 |
| **无毛利率分析** | 缺少毛利率字段，无法直观评估各商品/客户的盈利水平 |
| **币种处理缺失** | 虽然各单据支持多币种，但毛利表未做汇率换算，多币种混合计算 |

### 1.2 参考：金蝶云星辰的毛利表逻辑

金蝶云星辰的核心思路：

```
毛利 = 销售收入 - 出库成本
毛利率 = 毛利 / 销售收入 × 100%
净利润 = 毛利 - 费用（销售费用、采购费用等）
```

关键特征：
1. **成本由存货核算模块计算**：出库成本根据存货计价方法（移动加权平均、先进先出等）在出库时自动计算
2. **收入取自销售出库单**：而非销售订单
3. **成本取自出库成本**：而非入库单上的价格
4. **费用独立管理**：费用作为独立维度，可选择是否纳入毛利计算
5. **支持多维度分析**：按商品、客户、部门、业务员、日期等维度汇总
6. **支持多币种换算**：自动将外币金额按设定汇率换算为本位币，支持银行汇率和海关汇率

## 二、新毛利表设计

### 2.1 设计理念

**以出库单（delivery_orders）为核心**，每条出库商品行生成一行报表数据，所有关联数据通过业务链路自动获取。

**汇率换算原则**：
- 所有外币金额统一换算为人民币（CNY）显示
- 提供两种汇率视角：**银行汇率**（用于财务结算）和**海关汇率**（用于报关核算）
- 自动计算两种汇率换算后的差额（汇率差）

### 2.2 核心公式

```
销售收入(含税) = 出库数量 × 出库含税单价
销售收入(未税) = 出库数量 × 出库含税单价 ÷ (1 + 税率/100)

采购成本(含税) = 出库数量 × 采购含税单价（优先取采购订单，兜底取产品表）
采购成本(未税) = 采购成本(含税) ÷ (1 + 税率/100)

费用合计 = 采购费用 + 销售费用 + 入库费用 + 出库费用（均按金额比例分摊到商品行）

总成本 = 采购成本(未税) + 费用合计

毛利 = 销售收入(未税) - 总成本
毛利率 = 毛利 / 销售收入(未税) × 100%
```

> **费用说明**：四个环节的费用全部计入成本，参与毛利计算。
> - 采购费用：运输费、增值税、手续费、运营费、其他
> - 销售费用：运输费、手续费、其他
> - 入库费用：关税、运杂费、报关费、其他
> - 出库费用：快递费、运杂费、报关费、其他

### 2.2.1 汇率换算公式

**汇率获取规则**：
- **银行汇率**：根据出库单的 `entry_date` 所在周，从 `exchange_rates` 表查询（effective_week 匹配周一日期）
- **海关汇率**：根据出库单的 `entry_date` 所在月，从 `customs_exchange_rates` 表查询（effective_month 匹配月份）
- **兜底汇率**：优先使用订单上的 `exchange_rate` 字段，若为0或null则使用银行汇率

```
原始金额（外币） = 各项金额（按订单币种）

人民币金额（银行汇率） = 原始金额 × 银行汇率
人民币金额（海关汇率） = 原始金额 × 海关汇率

汇率差 = 人民币金额（银行汇率） - 人民币金额（海关汇率）
       = 原始金额 × (银行汇率 - 海关汇率)
```

**汇率换算应用场景**：
| 场景 | 使用的汇率 | 说明 |
|------|-----------|------|
| 销售收入换算 | 银行汇率 | 销售收款通常按银行汇率结算 |
| 采购成本换算 | 银行汇率 | 采购付款通常按银行汇率结算 |
| 关税计算 | 海关汇率 | 关税按海关汇率计算 |
| 汇率差计算 | 银行汇率 vs 海关汇率 | 反映汇率波动对利润的影响 |

#### D. 出库成本（入库单价取值逻辑）

**取值优先级**：
1. **优先**：通过出库单 `contract_number` → 销售订单 → 采购订单，从采购订单商品行中获取 `tax_included_price`

```
出库单.contract_number
  → 销售订单（按 contract_number 匹配）
    → 采购订单（按 related_sales_order_id 或 related_sales_orders 匹配）
      → 采购订单商品行.tax_included_price  ← 优先使用
  → 未匹配到采购订单
    → products.tax_included_price          ← 兜底使用移动加权平均价
```

| 字段 | 来源 | 说明 |
|------|------|------|
| 出库成本单价(含税) | 采购订单商品行 `tax_included_price` 或 `products.tax_included_price` | 优先取采购订单，兜底取产品表 |

| 出库成本(含税) | `quantity × 出库成本单价(含税)` | — |
| 出库成本(未税) | `quantity × 出库成本单价(未税)` | — |

> **说明**：对于有采购订单关联的出库单，使用采购订单上的含税单价作为成本，这是最准确的采购成本。对于没有关联采购订单的出库单（如直接销售、历史数据等），才使用产品表的移动加权平均价作为兜底。

| 人民币金额(银行汇率,未税) | `原币金额(未税) × 银行汇率` | 按银行汇率换算 |
| 人民币金额(海关汇率,含税) | `原币金额(含税) × 海关汇率` | 按海关汇率换算 |

| **汇率差(未税)** | `人民币(银行,未税) - 人民币(海关,未税)` | 反映汇率波动影响 |
| 银行毛利(CNY) | `人民币(银行,未税) - 总成本(银行汇率)` | 按银行汇率计算的毛利 |
| 海关毛利(CNY) | `人民币(海关,未税) - 总成本(海关汇率)` | 按海关汇率计算的毛利 |

> **说明**：
> - 当原币种为CNY时，银行汇率和海关汇率均为1，汇率差为0
> - 总成本中的费用也需要按相应汇率换算为人民币
> - 汇率差主要用于分析汇率波动对利润的影响，辅助决策

## 三、关键改动点

### 3.1 入库成本取值逻辑变更

**现状**：从入库单 `warehousing_items.tax_included_price` 读取，可能为0
**新方案**：优先从采购订单获取，兜底使用产品表移动加权平均价

```
旧逻辑：入库单价含税 = warehousingItem.tax_included_price（可能为0）

新逻辑：
  有采购订单时 → 采购订单商品行.tax_included_price（最准确的采购成本）
  无采购订单时 → products.tax_included_price（移动加权平均，兜底）
```

**理由**：
- 有采购订单关联时，采购订单上的含税单价是实际发生的采购成本，最为准确
- 无采购订单时，使用产品表的移动加权平均价兜底
- 两种情况都能保证不为0，解决了原入库单商品行价格为0的问题

### 3.2 出库成本独立计算

**现状**：毛利 = 出库未税金额 - 入库金额(未税) - 关税
**新方案**：毛利 = 出库未税金额 - 出库成本(未税)

```
旧逻辑：毛利 = amountExcluded - warehousingAmount - tariffPerItem
新逻辑：毛利 = salesAmountExcluded - outboundCostExcluded
```

**理由**：
- 与金蝶一致：毛利 = 收入 - 出库成本
- 出库成本使用移动加权平均价，是真正的"成本"
- 入库金额和入库费用作为独立的参考信息展示，不参与毛利计算

### 3.3 费用处理方式

**现状**：仅关税参与毛利计算，其他费用独立展示
**新方案**：四个环节的费用全部计入成本，参与毛利计算

```
旧逻辑：毛利 = 收入 - 入库成本 - 关税

新逻辑：
  费用合计 = 采购费用 + 销售费用 + 入库费用 + 出库费用
  总成本 = 采购成本(未税) + 费用合计
  毛利 = 收入(未税) - 总成本
```

### 3.4 匹配链路优化

**现状**：出库单 → 销售订单 → 采购订单 → 入库单（逐层匹配，任一断链则数据缺失）
**新方案**：成本取值采用"优先+兜底"策略

```
旧链路：delivery_orders → sales_orders → purchase_orders → warehousing_orders
        （入库单价从入库单读取，断链则为0）

新链路：
  成本：出库单 → 销售订单 → 采购订单 → 采购订单商品行.tax_included_price（优先）
        出库单 → 无法匹配采购订单 → products.tax_included_price（兜底）
  入库信息：delivery_orders → sales_orders → purchase_orders → warehousing_orders（辅助参考）
```

### 3.5 汇率换算与汇率差计算

**现状**：多币种混合计算，未做汇率换算，无法反映真实人民币利润
**新方案**：自动换算为人民币，支持银行汇率和海关汇率两种视角

```
旧逻辑：直接使用外币金额计算毛利，不同币种混合汇总

新逻辑：
  1. 根据出库日期自动匹配银行汇率（按周）和海关汇率（按月）
  2. 将所有外币金额分别按两种汇率换算为人民币
  3. 计算汇率差 = 银行汇率金额 - 海关汇率金额
  4. 分别计算按银行汇率和海关汇率的毛利
```

**汇率匹配规则**：
- **银行汇率**：出库日期所在周一 → `exchange_rates.effective_week`
- **海关汇率**：出库日期所在月 → `customs_exchange_rates.effective_month`
- **兜底规则**：若汇率表无记录，使用订单上的 `exchange_rate` 字段；若仍为0或null，默认为1

**应用场景**：
- 销售收入、采购成本、销售费用、采购费用 → 使用银行汇率换算
- 关税 → 使用海关汇率换算
- 汇率差 → 辅助分析汇率波动对利润的影响

### 3.6 结算信息查询

**现状**：毛利表不显示结算状态，无法判断收入是否已确认
**新方案**：关联应收单和核销单，显示完整的结算信息

```
旧逻辑：仅显示销售订单的结算状态（settlement_status），信息不完整

新逻辑：
  1. 通过出库单号关联应收单（receivables.source_bill_id = delivery_orders.order_number）
  2. 从应收单获取：应收金额、已结算金额、待结算余额、结算状态
  3. 通过应收单关联核销明细（write_off_items.source_id = receivable_id）
  4. 从核销单获取：最近核销日期、核销单号、核销次数
```

**数据关联链路**：
```
出库单(delivery_orders.order_number)
  → 应收单(receivables.source_bill_id = order_number AND source_bill_type = 1)
    → 核销明细(write_off_items.source_id = receivable_id)
      → 核销单(write_off_documents.write_off_id)
```

**业务意义**：
- 结算状态为"已结算"的订单，收入已确认，毛利更可靠
- 结算状态为"未结算"的订单，收入未确认，存在坏账风险
- 核销日期可用于分析回款周期，评估客户信用

### Phase 1：后端 Controller 重构

## 五、新旧逻辑对比

| 维度 | 旧逻辑 | 新逻辑（参考金蝶） |
|------|--------|-------------------|
| 成本来源 | 入库单商品行 `tax_included_price`（可能为0） | 优先：采购订单含税单价；兜底：products 表移动加权平均价 |
| 毛利公式 | 出库未税 - 入库未税 - 关税 | 出库未税 - 采购成本未税 - 全部费用 |
| 费用处理 | 仅关税参与毛利，其余费用独立展示 | 四环节费用全部计入成本，参与毛利计算 |
| 毛利率 | 无 | 毛利 ÷ 出库未税金额 |
| 匹配依赖 | 强依赖入库单匹配 | 弱依赖（成本不依赖入库单匹配） |
| 币种处理 | 未处理，多币种混合计算 | 自动换算为人民币，支持银行汇率和海关汇率双视角 |
| 汇率差 | 无 | 自动计算银行汇率与海关汇率的差额，辅助分析汇率风险 |
| 结算信息 | 无 | 显示已结算金额、待结算余额、结算状态、结算日期 |

## 六、风险与注意事项

1. **products 表价格准确性**：移动加权平均价依赖入库单创建时的正确计算，需确保历史数据的 `tax_included_price` 已正确更新
2. **出库时点 vs 入库时点**：如果出库发生在最后一次入库之前，出库成本用的是出库时的移动加权平均价（而非最新的），这是正确的业务逻辑
3. **退货处理**：出库退货（退货单）应扣减收入，入库退货应影响库存和移动平均价，需确认退货单逻辑是否完善
4. **汇率数据完整性**：需确保汇率表中有对应周/月的汇率数据，否则需使用兜底汇率（订单上的 exchange_rate 字段）
5. **汇率时效性**：银行汇率按周更新，海关汇率按月更新，需确认用户维护的汇率是否及时
6. **性能考虑**：汇率查询需要批量处理，建议一次性查询所有需要的汇率，避免N+1查询问题
